# Story 5.6 — Rematch automatique après annulation de trajet (Backend)

**Date:** 2026-07-18
**Status:** ✅ Complète

## Résumé

Quand un voyageur annule son trajet (`cancelTrip`), chaque expéditeur affecté reçoit désormais des suggestions de trajets alternatifs pertinentes (fenêtre de 3 jours, même corridor, capacité suffisante) au lieu de rester sans issue après remboursement. La logique de matching a été extraite dans un nouveau `RematchService` dédié, corrigeant deux bugs de l'implémentation historique (suggestions générées pour le premier expéditeur affecté seulement, aucune vérification de capacité), et la notification `TRIP_CANCELLED` porte désormais un deep link conditionnel (`cancellationId`) exploitable par le front.

## Fichiers créés

- `src/main/java/com/dony/api/cancellation/RematchService.java` — génère les suggestions de rematch pour chaque `CancellationEntity` créée par `cancelTrip` (une par bid/expéditeur affecté), via une `Specification` composée réutilisant `matching/AnnouncementSpecification`.
- `src/test/java/com/dony/api/cancellation/RematchServiceTest.java` — tests unitaires Mockito (fenêtre, capacité, exclusions, tri, limite, multi-expéditeurs, cas GRID `weightKg == null`).
- `src/test/java/com/dony/api/cancellation/RematchSpecificationDbTest.java` — tests `@DataJpaTest` sur une vraie DB H2/Hibernate exerçant `buildAlternativesSpec` (seul niveau où le bug de null-safety sur `weightKg` se manifeste réellement).

## Fichiers modifiés

- `src/main/java/com/dony/api/cancellation/CancellationService.java` — `cancelTrip` délègue la génération de suggestions à `RematchService.generateForCancellations(...)` (ancienne méthode privée `generateRematchSuggestions`, full scan + 1er expéditeur seulement, supprimée) ; `buildRematchSuggestionDtos` réécrite pour batch-charger annonces alternatives et voyageurs (`findAllById`, plus de N+1) et enrichir les DTOs avec les infos voyageur.

- `src/main/java/com/dony/api/cancellation/events/TripCancelledEvent.java` — +champ additif `Map<UUID, RematchBySenderInfo> rematchBySender` (clé = senderId, `RematchBySenderInfo(cancellationId, suggestionCount)`, record imbriqué défini dans l'event pour éviter une dépendance `notifications/` → `cancellation/`) ; nouveau constructeur complet 8-arg, les 3 constructeurs existants (7/6/5 args) préservés et délèguent avec `Map.of()`.
- `src/main/java/com/dony/api/notifications/NotificationDispatcher.java` — `onTripCancelled` rendu conditionnel selon `RematchBySenderInfo` (3 branches : legacy, ≥1 suggestion avec deep link, 0 suggestion) ; passé de `@EventListener @Async` à `@TransactionalEventListener(phase = AFTER_COMMIT) @Async` (fix post-revue).
- `src/main/java/com/dony/api/matching/BidService.java` — `toResponse` calcule `tripCancellationId`/`tripCancellationRematchStatus` via un discriminant par élimination (voir « Pièges »).

## Comment ça fonctionne (pour la maintenance)

### Vue d'ensemble du flux

1. Le voyageur appelle `POST /cancellations` (`CancellationService.cancelTrip`) pour annuler son trajet complet.
2. L'annonce passe à `CANCELLED`, tous les bids actifs (`PENDING`, `PAYMENT_ESCROWED`, `ACCEPTED`) passent à `CANCELLED`, une `CancellationEntity` (`scope = HANDOVER`) est créée **par bid affecté**.
3. Pour **chaque** `CancellationEntity` créée, `RematchService.generateForCancellations` :
   - construit une `Specification<AnnouncementEntity>` (statut `ACTIVE`, même corridor, fenêtre `[aujourd'hui, departureDate_annulé + 3j]` bornes incluses, capacité `availableKg ≥ weightKg` du bid annulé si connu, visibilité publique, non bloqué, exclusion de l'annonce annulée et de toutes les annonces du voyageur qui annule) ;
   - exécute la requête en base (`announcementRepository.findAll(spec)`), trie en mémoire (date croissante puis note voyageur décroissante) et garde les 5 premières ;
   - persiste une `RematchSuggestionEntity` par alternative retenue et passe `cancellation.rematchStatus` à `"SUGGESTED"` si au moins une suggestion existe.
4. `cancelTrip` agrège le résultat (`Map<senderId, RematchInfo(cancellationId, suggestionCount)>`) et publie `TripCancelledEvent` enrichi de cette map.
5. `NotificationDispatcher.onTripCancelled` (déclenché **après commit** de la transaction) envoie, pour chaque expéditeur affecté, une notification `TRIP_CANCELLED` dont le corps et la présence de `cancellationId` dans `data` dépendent du nombre de suggestions.
6. L'expéditeur peut consulter/relire ses suggestions via `GET /cancellations/{id}/rematch-suggestions` (déjà existant, DTO enrichi).
7. Le champ `tripCancellationId`/`tripCancellationRematchStatus` exposé sur `BidResponse` permet au front d'afficher un CTA « Voir les trajets alternatifs » sur le talon du bid annulé sans requête supplémentaire.

### Points d'entrée API

- `POST /api/v1/cancellations` — annule le trajet entier (voyageur uniquement, propriétaire de l'annonce). Déclenche la génération des suggestions ; inchangé côté contrat HTTP (la réponse continue de renvoyer les suggestions du **premier** expéditeur affecté, comportement historique consommé par l'écran voyageur post-annulation).
- `GET /api/v1/cancellations/{cancellationId}/rematch-suggestions` — inchangé dans sa signature, réservé au participant (expéditeur ou voyageur du bid concerné, 403 sinon) ; le `RematchSuggestionDto` retourné est désormais enrichi de `travelerFirstName`, `travelerRating`, `travelerRatingCount`.

### Entités JPA impliquées

- `AnnouncementEntity` → table `announcements` — filtré/trié par `RematchService` ; aucune colonne nouvelle.
- `CancellationEntity` → table `cancellations` — colonne `rematchStatus` (déjà existante depuis V8, `"NONE"` par défaut) enfin utilisée, passe à `"SUGGESTED"` par `RematchService`.
- `RematchSuggestionEntity` → table `rematch_suggestions` (déjà existante depuis V8) — une ligne par (cancellationId, announcementId) suggérée ; aucune contrainte d'unicité forcée en base, la déduplication vient de la logique applicative (une génération par cancellation).
- `BidEntity` — source de `weightKg` (peut être `null` pour un bid en mode GRID) et `senderId` utilisés pour filtrer/attribuer les suggestions.
- `UserEntity` — `averageRating`/`ratingCount` du voyageur alternatif, batch-chargés (`findAllById`) pour le tri et l'enrichissement DTO.

### Logique métier critique

- **Génération par cancellation, pas par annulation** : `generateForCancellations(cancelled, affectedBids, cancellations)` boucle sur `affectedBids` et `cancellations` **index à index** — c'est le fix du bug historique où un seul expéditeur (le premier de la liste) recevait des suggestions ; désormais chaque expéditeur affecté a sa propre recherche filtrée sur la capacité de **son** bid.
- **Capacité conditionnelle** : `weightKg` peut être `null` pour un bid GRID. Dans ce cas, le filtre `minAvailableKg` n'est simplement pas ajouté à la `Specification` (pas de contrainte de capacité connue) plutôt que de planter — voir « Pièges ».
- **Tri hybride SQL + mémoire** : le filtrage dur (statut, corridor, fenêtre de dates, capacité, visibilité, blocage) est fait en SQL via `Specification` (efficace, pas de full scan) ; le tri (date croissante puis note voyageur décroissante) est fait en mémoire car la note voyageur n'est pas une colonne de `announcements` — nécessite un second aller-retour `userRepository.findAllById`.
- **Discriminant `tripCancellationId` par élimination** : voir « Pièges » ci-dessous, c'est la partie la plus fragile de cette story.
- **Notification unique et conditionnelle** : pas de seconde notification créée pour le rematch — le corps de la notification `TRIP_CANCELLED` existante change selon `suggestionCount` (0 vs ≥1, singulier vs pluriel), et `cancellationId` n'apparaît dans `data` que si `suggestionCount > 0` (sinon pas de deep link vers un écran vide côté front).

### Events Spring publiés / écoutés

- `TripCancelledEvent` (publié par `CancellationService.cancelTrip`, inchangé pour `cancelAfterHandover` qui utilise le constructeur legacy 6-arg → `rematchBySender` vide) — écouté par `NotificationDispatcher.onTripCancelled` (nouveau comportement conditionnel) ainsi que par les listeners de remboursement déjà existants (`TripCancelledEventListener` en payments, `WalletCancellationListener`, `BidCancelledCommissionRefundListener`, `CardCommissionTripCancelRefundListener`), non modifiés par cette story.
- `NotificationDispatcher.onTripCancelled` est passé de `@EventListener @Async` à `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) @Async` (fix appliqué en revue finale, voir « Pièges »).

### Pièges et points d'attention

- **Invariant d'alignement `affectedBids[i]` ↔ `cancellations[i]`** : `RematchService.generateForCancellations` suppose que les deux listes sont de même taille et alignées index à index (même ordre que dans `CancellationService.cancelTrip`, où `cancellations` est construite par un `for (BidEntity bid : affectedBids)` qui ajoute dans le même ordre). Toute modification future de `cancelTrip` qui changerait l'ordre de construction de l'une des deux listes sans l'autre casserait silencieusement l'attribution des suggestions au mauvais expéditeur — aucune vérification défensive de taille/ordre n'existe actuellement.
- **`weightKg == null` (bids GRID) ne doit jamais throw** : `bid.getWeightKg()` est `null` pour les bids en mode GRID. Un premier passage de cette implémentation passait ce `null` tel quel à `AnnouncementSpecification.minAvailableKg(...)`, qui appelle `cb.greaterThanOrEqualTo(root.get("availableKg"), null)` → `NullPointerException` à la construction du predicate JPA. Comme `generateForCancellations` tourne **dans la même transaction** que `cancelTrip` (`@Transactional`), cette exception aurait fait **rollback toute l'annulation** dès qu'un bid GRID actif était affecté. Fix : le filtre `minAvailableKg` n'est ajouté à la `Specification` que si `weightKg != null` (`RematchService.buildAlternativesSpec`). Seul un test contre une vraie DB (`RematchSpecificationDbTest`) peut prouver ce comportement — un mock Mockito n'invoque jamais le vrai `CriteriaBuilder`.
- **Discriminant `tripCancellationId` par élimination, pas par un champ dédié** : il n'existe **aucun champ discriminant explicite** sur `CancellationEntity` permettant de distinguer "annulation de trajet entier" (`cancelTrip`) d'un no-show expéditeur ou d'une "annulation après remise" — ces trois flux créent tous une `CancellationEntity` avec `scope = HANDOVER` (valeur par défaut, jamais explicitement fixée par les 2 derniers). `BidService.toResponse` calcule donc `tripCancellationId` par élimination : `announcement.status == CANCELLED` **ET** `cancellation.reason` n'est **aucune** des constantes programmatiques connues des autres flux HANDOVER (`NON_TRIP_HANDOVER_REASONS = {SENDER_NO_SHOW, SENDER_CANCEL_AFTER_HANDOVER, TRAVELER_CANCEL_AFTER_HANDOVER}`). Piège découvert en revue : le flux `cancelAfterHandover` (annulation après remise) est **aussi** `scope = HANDOVER` — il doit impérativement rester dans `NON_TRIP_HANDOVER_REASONS`, sinon une annulation après remise se ferait passer pour une annulation de trajet complet côté front. Un second piège corrigé en revue : `AnnouncementRepository.cancelOpenAnnouncementsByUserId` (bulk update JPQL appelé par `AccountDeletionListener` à la suppression de compte) pose aussi `AnnouncementStatus.CANCELLED` **sans créer de `CancellationEntity`** — un `grep` naïf sur `setStatus(AnnouncementStatus.CANCELLED)` seul aurait manqué ce site. Si un futur flux écrit une nouvelle valeur `reason` programmatique fixe sur une cancellation `scope=HANDOVER`, il **doit** être ajouté à `NON_TRIP_HANDOVER_REASONS` sous peine de faux positif silencieux. Dette assumée : un champ discriminant dédié (ex. `cancellationType` enum) serait plus robuste mais nécessiterait une migration Flyway, explicitement hors scope.
- **`@TransactionalEventListener(AFTER_COMMIT)` sur `onTripCancelled`** : initialement `@EventListener @Async` (comme le reste de `NotificationDispatcher`), corrigé en `@TransactionalEventListener(phase = AFTER_COMMIT) @Async` en revue finale — sans ça, la notification portant le deep link `cancellationId` pourrait partir **avant** que la transaction `cancelTrip` (qui crée `CancellationEntity` et `RematchSuggestionEntity`) ne soit committée : en cas de rollback, notification trompeuse envoyée pour rien ; en cas de race, `GET /cancellations/{id}/rematch-suggestions` pourrait retourner 404 si le client tape trop vite sur la notification. Pas de `@Transactional(propagation = REQUIRES_NEW)` sur cette méthode (contrairement aux listeners qui mutent un solde) : elle ne fait que lire et notifier, elle suit exactement le pattern de `TripCancelledEventListener` (payments), pas celui des listeners de commission/wallet.
- **Aucune migration Flyway** : `rematch_suggestions` et `cancellations.rematch_status` existent déjà depuis V8 — cette story ne fait qu'enfin les utiliser correctement (`rematch_status` restait bloqué à `"NONE"` auparavant, `rematch_suggestions` n'était alimentée que pour le premier expéditeur).
- **N+1 déjà traité** : `buildRematchSuggestionDtos` batch-charge les annonces alternatives (`announcementRepository.findAllById`) et les voyageurs (`userRepository.findAllById`) en un seul aller-retour chacun, jamais un `findById` par suggestion.

## Décisions techniques

- **Extraction en `RematchService` dédié** plutôt que de garder la logique inline dans `CancellationService` : suit la structure de package déjà documentée (`cancellation/RematchService.java` anticipé dans l'architecture), isole une logique de matching complexe et testable indépendamment, et évite d'alourdir davantage `CancellationService.cancelTrip` qui gère déjà beaucoup de responsabilités (statuts, audit, remboursements, event).
- **Réutilisation des `Specification` existantes de `matching/AnnouncementSpecification`** (`hasStatus`, `hasDepartureCity`, `hasArrivalCity`, `departureDateFrom/To`, `minAvailableKg`, `publicOrOpenSurplus`, `notBlockedBy`) plutôt que de réécrire une requête JPQL/Criteria ad hoc : garantit la cohérence avec la visibilité du feed de recherche public expéditeur (même règles de blocage/visibilité), et ces Specifications sont déjà individuellement testées.
- **Filtre `minAvailableKg` conditionnel plutôt qu'un défaut arbitraire** (ex. `weightKg = 0`) pour les bids GRID : un défaut à 0 aurait été un choix silencieux et arbitraire (masquer le cas au lieu de le documenter) ; l'absence de filtre est explicite et documentée en javadoc comme une "dette conservatrice" (peut suggérer une annonce à capacité quasi nulle) plutôt qu'un crash.
- **Discriminant `tripCancellationId` par élimination (`reason` + `announcement.status`) plutôt qu'un champ dédié sur `CancellationEntity`** : la contrainte "aucune migration Flyway" pour cette story interdisait d'ajouter un champ discriminant propre (ex. `cancellationType` enum). Le choix par élimination est documenté comme une dette assumée dans le code (javadoc + commentaires) — un futur ticket pourrait introduire un champ dédié si ce genre de faux positif redevient un problème récurrent.
- **`@TransactionalEventListener(AFTER_COMMIT)` sans `REQUIRES_NEW` sur `onTripCancelled`** : ce listener ne fait que lire (résoudre les données à notifier) et appeler `notificationService.persist` + `fcmService.sendToUser`, sans muter d'état financier nécessitant une transaction isolée — il suit donc le pattern du listener `TripCancelledEventListener` (payments) plutôt que celui des listeners de commission/wallet qui, eux, ont besoin de `REQUIRES_NEW` pour isoler leurs écritures.
- **Une seule notification `TRIP_CANCELLED` enrichie plutôt qu'une notification dédiée au rematch** : évite de doubler le bruit de notification pour l'expéditeur (déjà notifié du remboursement) et garde le contrat de notification existant stable — seul le corps/`data` change selon le contexte.
